### Welcome to the .NET **nanoFramework** metadata processor repository

This repo contains .NET **nanoFramework** metadata processor tool.
It's a console app that performs various tasks when running a build of a C# project, like parsing the PE file generated by Roslyn, generating the PDBX files, generate the stubs for native code.
Is part of .NET **nanoFramework** toolbox, along with other various tools that are required in .NET **nanoFramework** development, usage or repository management.

Version 2.0 is a C# application adapted from the original work of [Oleg Rakhmatulin](https://github.com/OlegRa).
Version 1.0 was a Visual C++ application adapted from .NETMF toolbox.

## Using the metadata processor

The metadata processor is available in two packages.

The main use of the metadata processor is packaged as a MSBuild task: [nanoFramework.Tools.MetadataProcessor.MsBuildTask](https://www.nuget.org/packages/nanoFramework.Tools.MetadataProcessor.MsBuildTask). The task is well integrated into the .NET **nanoFramework** build system and is distributed as part of the VS extensions. Almost all use cases can be addressed by the build system as it is, or by setting build variables for, e.g., additional logging.

There are few use cases where the build task cannot be used. E.g., in software that generates source code at runtime, compiles the code via Roslyn, executes it on the virtual device, and uses the output for further processing. The metadata processor is required as a companion to Roslyn to convert the generated .NET assemblies to .NET **nanoFramework** .pe assemblies. The second package, [nanoFramework.Tools.MetadataProcessor.CLI](https://www.nuget.org/packages/nanoFramework.Tools.MetadataProcessor.CLI), contains a CLI version of the tool for this purpose. It is packaged as content: if added to a project, the tool will be distributed with the results of that project. If the package is added to a non-SDK-style project (e.g., .NET Framework project), make sure to set the *Copy to Output Directory* property for the files, as the package manager does not automatically do that. The code in the project should run the CLI with arguments *-loadhints*, *-parse* and *-compile* (in that order!) to create the .pe assembly.

## Developers guide

### Cloning the repository

After cloning the repository, instantiate the submodules with:

```shell
git submodule update --init --recursive
```

After which the NuGet packages in both the main solution and the mscorelib solution included within a submodule have to be restored. These have to be restored individually.

### Build hosts and package layout

Source builds require the .NET 10 SDK selected by `global.json` and Visual Studio 2026
MSBuild 18 for the solution's Framework projects. This is separate from the hosts that
can **run** the packaged task:

| Consumer | Payload | Host |
|---|---|---|
| VS2019 extension / legacy project | `tasks\net472` | Framework MSBuild 16.11, x86 |
| VS2022 extension / legacy project | `tasks\net472` | Framework MSBuild 17, x64 |
| VS2026 extension / legacy project | `tasks\net472` | Framework MSBuild 18, x64 |
| SDK / `dotnet build` | `tasks\net10.0` | .NET 10 MSBuild |
| Standalone console | `MetadataProcessor` content directory | .NET Framework 4.7.2 or newer |

The task package is a **tool**, not an application library: it has no `lib` assets.
Each task directory carries its own runtime dependencies; the modern directory also
contains the dependency manifest and runtime-specific assets. Microsoft.Build assemblies
are supplied by the host, never deployed with MDP. The Framework task compiles against
the MSBuild 16.11 API baseline, independently of the source-build toolchain.

VSIX projects should reference the package with `IncludeAssets="build"` and
`PrivateAssets="all"`. Its `build` targets stage the authoritative `tasks\net472`
payload into the existing `MSBuild\nanoFramework\v1.0` location; they do not register
tasks unconditionally or collect unrelated extension output DLLs.
SDK consumers exclude the package's build imports and register the assembly from
`tasks\net10.0` on Core MSBuild or `tasks\net472` on Framework MSBuild.
`NF_MDP_MSBUILDTASK_PATH` continues to mean the directory containing the task DLL
and its complete dependency payload, not the package root.

The CLI remains a Framework executable. Keep its `.exe.config` and all adjacent
dependencies together. Both `content\MetadataProcessor` and
`contentFiles\any\any\MetadataProcessor` layouts are retained. Pack a built console
with `nuget pack MetadataProcessor.Console\package.nuspec -Properties configuration=Release`
and the version computed by Nerdbank.GitVersioning.

The .NET 10 SDK feature band matters for **SDK-style** Visual Studio projects:
10.0.1xx has a VS2022 17.14 compatibility bridge, while 10.0.2xx and later require
VS2026/MSBuild 18. The `global.json` source-build policy selects 10.0.4xx; it does not
promise SDK-style VS2022 support. Legacy VS2022 `.nfproj` builds use the Framework
payload and do not require the modern task runtime. See Microsoft's
[SDK/Visual Studio compatibility matrix](https://learn.microsoft.com/en-us/dotnet/core/porting/versioning-sdk-msbuild-vs).
Retargeting does not make the MDP bitmap paths cross-platform: they still use
System.Drawing and need platform-specific qualification.

### Package regression gate

Run `eng\Verify-MdpPackage.ps1` against the **packed** task and console nupkgs, supplying
`-TaskPackage`, `-CliPackage` and `-MSBuild` with the installed host paths.
For modern MSBuild pass the SDK's `MSBuild.dll`; for Framework pass `MSBuild.exe`.
Build the Release test fixtures first, or supply `-Fixture` and `-StubsFixture`.
The gate extracts both packages into a temporary directory with spaces, invokes real conversions
and native-stub generation (including parallel invocations), and compares PE, semantic PDBX and native outputs across
hosts, both console content layouts and a restored PackageReference consumer. It also checks
CLI dependency output and failure diagnostics, and snapshots fixture directories before running.
PDBX comparison treats only the existing `DATATYPE_LAST_PRIMITIVE`/`DATATYPE_STRING`
enum aliases as equivalent; no production serialization or debug-format change is made.

Release qualification must run this gate before signing/publication, inspect both
consumer VSIX archives, and include clean-install/upgrade, IDE build and debugger smoke
checks on supported Visual Studio releases. Publish a new MDP version first, then release
the matching VSIX/SDK consumers; do not replace an already-published package in place.

### Adding projects to the solution

When adding a project to the solution the following points have to be kept in mind for configuring the project and solution:

- nanoFramework projects (.nfproj) have to be build in `AnyCPU` configuration.
- Use x64 MSBuild for source builds. Keep task DLLs AnyCPU so the same Framework payload also loads in VS2019's x86 MSBuild.
- Any nanoFramework projects (.nfproj) that are required for Unit Tests have to have their build configuration changed so they don't build. Building those has to be added to the pre-build event of the Unit Test project that will be using it. See the [prebuild event](https://github.com/nanoframework/metadata-processor/blob/bcb82f6c9153cdc3863abf6fcc5b589437408b28/MetadataProcessor.Tests/MetadataProcessor.Tests.csproj#L118-L128) for the MetadataProcessor.Tests project. When adding nanoFramework projects to the pre-build event it is important to add the `-nr=False` flag<sup>[1]</sup>.

1. This flag disables "nodeReuse", this is needed as a custom MsBuildTask is used which also gets rebuilt. "NodeReuse" keeps instances of MsBuild running which interferes with the rebuilding of the custom MsBuildTask.

### Code sync between MDP, native code and other tools

There are several code snippets, structures and details that are shared between the metadata processor, the native code and other tools. These need to be kept in sync.
For those that need to be keep in sync with native code, there is a tag `<SYNC-WITH-NATIVE>` in a comment before the relevant code snippet.
For sync with Visual Studio extension, the tag `<SYNC-WITH-VS>` is used.
For sync with the debugger, the tag `<SYNC-WITH-DEBUGGER>` is used.

### Miscellaneous

Install the nanoCLR .NET tool before running `ClrIntegrationTests` locally. The tool currently requires the .NET 8 runtime:

```shell
dotnet tool install --global nanoclr
```

For an existing installation, use `dotnet tool update --global nanoclr`. The tests do not install or update the tool; the Azure DevOps pipeline installs it in a job-local directory before running tests.

The .NET tool package and native CLR instance have **independent** channel settings:

- **nanoCLR .NET tool package:** locally, the commands above select stable packages; adding `--prerelease` includes preview packages. To switch from a newer preview package to an older stable package, uninstall the tool first, then install it without `--prerelease`. The pipeline boolean parameter `nanoClrToolUsePreview` controls `--prerelease` through the installation task's `NF_MDP_NANOCLR_TOOL_USE_PREVIEW` variable.
- **Native nanoCLR instance:** tests run `nanoclr instance --update` before execution. Locally, `NF_MDP_NANOCLR_INSTANCE_USE_PREVIEW=true` adds `--preview`; `false` or unset selects stable releases. In CI, the boolean parameter `nanoClrInstanceUsePreview` sets this environment variable and defaults to `false`.

Both pipeline parameters default to `false` (stable). PR builds targeting `develop` override **both** selections to include previews for vNext testing. The nanoCLR setup and test steps are PR-only; manual pipeline runs currently skip them. Outside that PR override, selecting preview tool packages does not select preview native CLR instances, and vice versa.

To use a locally built DLL instead, set the environment variable `NF_MDP_NANOCLR_INSTANCE_PATH` to its full path. This selects `NanoClrLocalInstance` and skips the instance update, taking precedence over the stable/preview setting.

Without a local DLL override, `instance --update` must succeed; a nonzero exit fails initialization before `instance --getversion` or any tests.

For CI testing against a specific nf-interpreter build, add `[tested against nanoclr buildId NNN]` to the PR description. The pipeline downloads that build's `nanoclr_dll` artifact and passes its DLL path to the tests through the same environment variable.

The tests capture nanoCLR diagnostic output, including stderr, versions and the selected DLL. Use VSTest's `/Logger:"console;verbosity=detailed"` option to see output from passing tests in the console; the pipeline enables this option.
